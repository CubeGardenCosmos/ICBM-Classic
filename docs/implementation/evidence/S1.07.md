## 与步骤卡的差异

- **能力部分下沉到 S1.10（协调者裁决，本步转述）**：步骤卡 S1.07 的“改动文件”含 `lib/lookup/IcbmLookups.java`、`api/caps/**`、`lib/capability/**`。
  但 `api/caps/**`（`IEMPReceiver`、`IExplosive`、`IGPSData`、`IMissileHolder`）与 `lib/capability/**` 的实现依赖
  **S1.08 的 `api/actions`（`IAction` 等）** 与 **S4 的 `api/missiles`（`IMissile` 等）**，而这两个包在仓库现状下尚未移植
  （其接口仍停留在 1.12 签名，且 S1.08/S4 排在 S1.07 之后）。因此“步骤卡的依赖顺序在仓库现状下不可满足”：
  若在本步强做 `api/caps` 与 `lib/capability`，必须提前移植 `api/actions`、`api/missiles` 才能编译，属超出本步范围且违反总目录顺序。
  协调者据此裁决：**本步只做能量核心**，能力映射部分（`IcbmLookups`、`api/caps/**`、`lib/capability/**`、`CapabilityPrefab`、数据附件）
  整体下沉到 **S1.10**（公共 API 签名迁移之后，此时 `api/actions`/`api/missiles` 已就绪）。
  账本中这些文件写 `MERGED → S1.10 建立（依赖 S1.08 的 api/actions 与 S4 的 api/missiles）`，步骤列 `S1.10`；
  未创建任何 `IcbmLookups`/`api/caps`/`lib/capability`/数据附件文件，也未在注释中假称已完成。
- **`has(long)` 返回类型**：步骤卡骨架草拟注释写“`long has(...)`”，energy-fe.md §4 与其 javadoc 语义为布尔判断，
  故按 §4 采用 `public boolean has(long amount)`（任务卡亦明确“按 energy-fe.md §4 用 boolean”）。
- **`getStored()` 的容量夹取**：energy-fe.md §4 骨架写 `stored`，任务卡与 §4 的 JUnit 要求明确为 `Math.min(stored, capacity)`，
  故采用后者（容量运行时变小不超容量，且不修改内部 `stored`，`setStored` 时才夹取写回）。
- **`EnergyRules` 方法集**：仅 `ignoresPower()` 与 `consumeOrFree(IcbmEnergyBuffer, long)` 两项，未添加容量/消耗常量（按任务卡，那些在 config 各配置类）。
