## 1. 测什么、怎么测

重新生成路径完全走生产代码（S4.03）：`MissileTrackerHandler.simulateMissile(missile)` 把导弹写入
`MissileTrackerWorld` SavedData，`MissileTrackerWorld#runSimulationTick(level)` 推进模拟时间，
`ticksLeftToTarget<=0` 时进入 `missileSpawnList`，`preLoadChunkTimer` 归零后由
`spawnMissileOnDestination()` 重新生成实体（位置 `(target.x, simulation_enter_height, target.z)`、
速度 `(0, -simulation_enter_speed, 0)`、`DeadFlightLogic(100)`）。

| 测量量 | 取值方式（API / tick） |
|---|---|
| 重新生成点到目标的水平距离 | 重新生成的实体的 `getX()/getZ()` 与 `MissileTrackerData.targetPos` 的水平差，在同一 tick 内（重新生成的那一 tick，同步执行） |
| 重新生成高度 | 重新生成的实体的 `getY()`（= `ConfigMissile.SIMULATION_ENTER_HEIGHT`） |
| 到落地的 tick 数 | `TrajectoryPredictor.predictImpact(pos, motion, ZERO, radarY, ConfigAbm.PREDICTION_MAX_TICKS)`，即雷达自己用的外推；另记录 `RadarTrack.ticksToImpact`（真实跟踪值，逐 tick 采样） |
| 是否拦截成功 | `EngagementRegistry.wasIntercepted(level, threatUUID)`；拦截 tick = 目标实体被移除的 tick 减去重新生成 tick；拦截距离 = 移除前最后一次采样的目标位置到发射点距离 |
| ABM 发射时刻与当时的态势 | 逐 tick 采样 `level.getEntitiesOfClass(EntityAntiBallisticMissile.class, …)` 并按 `getTargetId()==threatUUID` 过滤（避免同批其它测试的 ABM 混入）；首次出现的 tick、当时目标的高度/距离、`RadarTrack.status`、`ticksToImpact` |
| ABM 实际步长 | 逐 tick 采样同一 ABM（按实体 UUID 连续性）的 3D 位移，取最大值，并**断言** ≤ `ConfigAbm.FLIGHT_SPEED + 0.01`；同时在 `InterceptEvents.INTERCEPTED` 上挂**只观察**（返回 true）的监听器记录解析近炸那一 tick 的 `getPreviousPositionThisTick()`→`position()` 距离 |

场景布置：雷达（`detection_range = ConfigRadar.MAX_RANGE(500)`、`trigger_range = 20`、`ABM_ONLY`、逐 tick
补满电）+ 一座巡航发射器（同频道、装 1 枚 `anti_ballistic_missile`、逐 tick 补满电），目标为雷达位置。
结构原点区块即实体 tick 区块；`|local| ≤ 3`。

配置对比：`ConfigMissile.SIMULATION_ENTER_HEIGHT` 的值在运行时读出后 **×2 注入夹具**（
`buildReentryReplica()` 逐行镜像 `spawnMissileOnDestination()`，只替换高度/速度两个入参），
**没有写任何静态配置字段**。夹具与生产路径的一致性由 `recordsDefaultReentryGeometry` 断言
（同参数下重构实体与生产重新生成的实体位置、速度、飞行逻辑完全一致）。

## 3. 结论

1. **重新生成点是「目标正上方、`simulation_enter_height` 高度、水平距离 0」**，与 1.12 `MissileTrackerWorld#211-214`
   的 `TODO calculate arc position so we don't come in on top of the target` 一致（即 1.12 也是这个行为）。
   高度换算成预警时间：默认 ~412 tick、×2 时 ~862 tick（按 `simulation_enter_speed` 匀速）。
2. **重新生成高度不是可拦截性的限制**（修复制导缺陷后）：火控在目标进入 `engagement_range`(200) 时下令发射
   （实测下令时目标距发射点 174.97 / 169.34 格），ABM 以 `flight_speed`=4 格/tick 迎头，23~28 tick 完成拦截，
   远早于目标落地，`fuel_ticks`=200 远未用尽。修复前该结论被制导缺陷掩盖（见第 3 条与 §4）。
3. **修复前的「默认行命中 / ×2 行未命中」是缺陷造成的偶然结果**：ABM 单 tick 位移 = `flight_speed × |aim − position|`
   （实测 190.5~335.9 格），近炸（段-段最近距离）只在越界线段恰好穿过目标 2.5 格内时命中。默认行穿过（差 ~2.5 格）、
   ×2 行擦过（差 ~3 格）→ 后者让目标落到雷达上。该缺陷已按维护者裁决在 `lib` 侧修复（§4），
   修复后两行都正常命中（表格第 5/6 列）。
4. **`prediction_max_ticks` 与外推高度上限**：900 格重新生成高度下 `TrajectoryPredictor` 在 600 tick 内无法到达
   `floorY`（需要 862 tick）→ 返回 null。若 `use_missile_target_data=true` 且导弹自带有效目标坐标（本测量即如此），
   雷达改用目标坐标作为落点，航迹仍能成为 `THREAT`，交战不受影响（实测 ×2 行在 tick ~117 起转为 `THREAT`）。
   **[INFERENCE]**：若某型导弹没有目标坐标，900 格重新生成高度会让雷达在很长一段时间内只报 `DETECTED`，
   火控不会下令发射。

## 4. 发现的缺陷与修复（历史记录 + 本次跟进）

> 维护者裁决：修 `lib` 侧而不是调用点 —— `Rotation.rotateTowards` 的契约是「返回方向」（θ>max 分支本就返回
> 单位向量，`AbmMathTest:98` 已钉住 `opposite.length()==1`），θ≤max 分支返回调用方原样的 `desired` 破坏了该契约；
> 调用点 `AbmGuidance.guide()` 按「返回值是方向」`.scale(FLIGHT_SPEED)` 是合理用法。

**ABM 制导步长失控**：`Rotation.rotateTowards()`（`content/abm/math/Rotation.java`）在
`theta <= maxRadians` 分支 `return desired;` —— 返回的是**未归一化**的入参；`AbmGuidance.guide()`
（`content/abm/AbmGuidance.java:62`）把它 `.scale(ConfigAbm.FLIGHT_SPEED)` 后直接 `setDeltaMovement()`，
于是 ABM 每 tick 的速度 = `flight_speed × |aim − position|`。`AbmGuidance` 是该方法唯一的生产调用点
（`grep -rn "rotateTowards" src/main/java` 只有 `AbmGuidance:62`，其余是 `EntityProjectile#rotateTowardsMotion`，
无关）。JUnit `AbmMathTest:90` 传入的是 `new Vec3d(1, 1, 0).normalize()`，所以单测覆盖不到未归一化入参。

实测证据链：

- 默认行解析近炸的 tick：`abmPrev=(7786778.5, 55.7285, …)` → `position=(…, 391.63, …)`，**位移 335.9 格**
  （`INTERCEPTED` 监听器记录），且该位移方向 = `4 × (aim − position)`（用 `InterceptMath.solve()` 复算的
  aim 与实测位移方向/比例一致：Δx 恰为横向偏移的 4 倍）。
- ×2 行：ABM 采样到的最大步长 258.65 格/tick（`flight_speed=4` 的 64 倍），目标随后落地。
- 现有 ABM 测试之所以长期通过：目标在雷达正上方时，越界线段仍会穿过目标 2.5 格内，近炸按「线段最近距离」（§8.2）
  判定为命中（S7.04 的 `高速穿越` 用例即依赖该机制）。

**已实施修复**（`src/main/java/icbm/classic/content/abm/math/Rotation.java`，仅该分支）：

```diff
         double theta = Math.acos(clamp(a.dot(b), -1, 1));
         if (theta <= maxRadians)
         {
-            return desired;
+            // the function contract is "returns a direction": every other branch answers with a unit
+            // vector too, so the caller may scale the result by a speed (AbmGuidance does exactly that).
+            // Returning `desired` as-is made a non-unit desired input blow the caller's speed up.
+            return b;
         }
```

`AbmGuidance` 未改动。回归守卫：

- JUnit `AbmMathTest#rotatesTowardDesiredDirectionWithinAngularLimit` 增加：θ≤max 分支返回值长度为 1 且方向一致
  （含 `desired = (2,0,0)` 的已对齐用例）、**非单位 `desired = (0,7,0)` 用例（本缺陷的回归测试）**；原 `:90`
  的 `assertEquals(closeDesired, …)` 改为比较方向（内部归一化后与预归一化输入可能差 1 ulp，方向相同）。
  结果：`./gradlew test --tests 'icbm.classic.content.abm.math.*'` → `BUILD SUCCESSFUL`（4 个测试全过）。
- GameTest 集成级守卫：`SimulatedMissileGameTest` 逐 tick 采样同一 ABM 的 3D 位移（按实体的 UUID 连续采样，
  避免把两次发射混算），并**断言** `maxStep <= ConfigAbm.FLIGHT_SPEED + 0.01`。

修复前后实测对照（同场景、逐 tick 采样）：

| 场景 | 修复前 ABM 单 tick 最大位移 | 修复后 ABM 单 tick 最大位移 | 修复前近炸解析 tick 的位移 |
| --- | --- | --- | --- |
| 默认行（450） | 3.5（采样只覆盖 BOOST，解析发生在首个 GUIDE tick） | **4.0000000000** | 273.8 ~ 335.9 格（4 次全量跑） |
| ×2 行（900） | 190.5 ~ 258.7 格 | **4.0000000000** | 未命中（无解析） |

**配置注释提示（设计 §9 原意）**：`ConfigMissile.SIMULATION_ENTER_HEIGHT`/`SIMULATION_ENTER_SPEED` 的
`@ConfigEntry(comment=…)` 未加面向玩家的提示文案。本步未改，原因：(a) 提示内容取决于上面缺陷的处置
（修好后“来不来得及拦截”的结论会变）；(b) 改动会让 `run/datagen/config/icbmclassic/missile.json`
这个已入库的生成物失效，需要连同 `runDatagen` 一起重跑。建议由维护者连同缺陷修复一并决定。

## 5. 夹具约束与偏离

- **实体 tick 区域**：所有参与 tick 的实体都在结构原点区块内（雷达 local (2,1,2)、发射器 local (5,1,2)、
  重新生成点在同区块列的 y=450/900）。重新生成点在原点区块列内 → 框架本身把它标为 `ENTITY_TICKING`，
  重新生成的导弹确实被 tick（`recordsDefaultReentryGeometry` 断言 20 tick 下落 20.0 格）。
- **不使用 `ServerLevel#setChunkForced`**（S7.07 结论：会让 `GameTestInfo#tickInternal` 抛 NPE）：
  测试类静态注册 `MissileChunkEvent.Load` 监听器，只对本类夹具的目标区块（`SUPPRESSED_CHUNKS`）返回
  `false`（即不申请区块票据），其余区块一律放行，因此 `MissileTrackerGameTest` 的既有行为不变。
  生产路径的「重新生成」本身不受影响（`forceChunk` 之后无条件进入 spawn 队列）。
- **不改静态配置**：×2 场景用「运行时读取 + 注入夹具」（见 §1）。
- **同批并发隔离**：两个场景测试（默认/×2）用 `SCENE_RESERVED_UNTIL` 自续期预约互斥（各自逐 tick 续约，
  结束时自动过期），因为两部雷达的探测半径 500 会覆盖相隔 77 格的结构；ABM 采样按 `getTargetId()` 过滤，
  避免把邻居的 ABM 算进来。为此场景雷达的 `trigger_range` 取 20（只把瞄向本结构的导弹判为 `THREAT`）。
- 结构与雷达/发射器位置（实测绝对坐标示例，不同批次会不同）：radar 与 launcher 相距 3 格，两块结构相距 77 格。

## 8. [INFERENCE] 与未验证项

- **[INFERENCE]** 1.12 时代同样存在「正上方重新生成」，因此该行为不是 26.3 移植引入的（依据：`legacy-1.12` 的
  `MissileTrackerWorld#spawnMissileOnDestination` 逐行对应，含同样的 TODO 注释）。
- **[INFERENCE]** 玩家实际对局中（区块由玩家加载、导弹从 >500 格外来）重新生成时的高度/水平几何与夹具一致
  （本测量只覆盖了 `SIMULATION_ENTER_*` 与目标坐标，未覆盖「导弹自带目标数据坐标与保护区偏移」的组合）。
- **[INFERENCE]** 若 `use_missile_target_data=false`，900 格重新生成高度会让雷达长时间只报 `DETECTED`（见 §3 第 4 条）。
- **[INFERENCE] 两种「击毁」路径**：修复后 ABM 以正常速度接敌，可能由 ① ABM 近炸（写 `EngagementRegistry`，
  可被 `InterceptEvents.INTERCEPTED` 观察到）或 ② 来袭导弹自己的实体命中判定先打到 ABM（导弹空中爆炸，
  **不**写 registry）结束交战，取决于同一 tick 内两个实体的 tick 顺序。5 次全量跑中 4 次走 ①、1 次走 ②，
  两种结果都表示「导弹在空中被拦下」（y≈107~129，远高于地面）。本步测试对两者都放行并如实记录；
  若 S7.10/S7.11 需要「必须走近炸路径」的确定性，应把该顺序固定下来（例如让来袭导弹忽略实体命中），
  这属于新决策，本步不擅自改动。
- **未验证**（需重测）：`ConfigMissile` 注释文案；实机（客户端）表现——按 S7.11 人工门禁处理。
- **需重测（转交 S7.10）**：制导修复改变了 ABM 的飞行时间（不再瞬移），§11 中依赖「发射后极短时间命中」的场景
  都要重测：`单目标拦截`（80 格水平 + 60 格高、400 tick 预算是否仍够）、`不越权齐射`、`燃料耗尽自毁`（自毁时序）、
  `跨雷达去重`；`落点在外不交战` 与 `EMP 兜底` 与制导无关，顺带确认即可。
