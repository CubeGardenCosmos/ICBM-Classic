**与步骤卡骨架的差异**：骨架里的每个方法名/类名在 26.3 都存在，无改名。额外核实：
- `PalettedContainer#copy()` 走拷贝构造 → `Data.copy()` → `BitStorage.copy()` + `Palette.copy()`（`javap -c` 确认），因此快照是**深拷贝**、工作线程只读安全（反向验证 2 证明没有它测试会失败）。
- `GameTestSequence#tickAndContinue` 吞掉 `GameTestAssertException`（等待），`thenExecute` 走 `executeWithoutFail` → `GameTestInfo.fail`（立即失败），因此「等待全部变空气 → 断言 onComplete 只调用一次」两个语义都成立。

## 与步骤卡的差异

1. **`IThreadWork` 终态（步骤卡要求「增加 LevelSnapshot 参数」；任务书允许两案）**：采用**参数传递**方案，
   即 `boolean doRun(int steps, LevelSnapshot snapshot)` + `void onStarted(LevelSnapshot snapshot)`，保留
   `onCompleted()`/`getStepsRequired()`/`getStepsLeft()`；快照与任务一起入队（`WorkerThread` 内部 `record WorkEntry(IThreadWork, LevelSnapshot)`），
   `WorkerThreadManager.addWork(IThreadWork, LevelSnapshot)` 一并提交。理由：与步骤卡 §3 的字面要求一致，且「谁提供了哪个快照」在框架层显式可见，
   不需要每个工作对象自己持有快照字段；1.12 的 `addWork(IThreadWork)` 单参签名因此改为双参（`ThreadWorkBlast` 等调用点在 S3.02/S3.06 适配）。
   `ThreadWorkBlast` 的 `runFunction` 仍是 1.12 的 `BiFunction<Integer, Consumer<BlockPos>, Boolean>`：调用方（未来的 `BlastThreaded`）
   在闭包里捕获自己需要的快照，因此该方法体内不使用传入的 `snapshot` 参数（javadoc 已注明）。
2. **`Thread.stop()` 替代（任务书硬性要求）**：1.12 用 `Thread.stop()`；26.3 改为 `volatile boolean doRun` + `interrupt()`（打断空闲 `sleep(100)`）
   + `join(timeoutMs)`。`WorkerThread.stopTasks(long)` 与 `WorkerThreadManager.killThreads()`（先对所有线程 `signalStop()`，再用**总计 5 秒**的
   截止时间逐个 join）实现；线程停止时仍未启动的任务丢弃，并以 `logger().warn` 汇总报告（日志实测见验证 3 ①的 `Dropped 1 unfinished work task(s)`；
   在定稿的通过运行里为 0，不打印）。`WorkerThread#interrupt()` 覆写里 1.12 的 `error` 级日志降为 `debug`——interrupt 现在是正常停机路径，
   报 error 会让开启 `debug_threads` 的用户每次关服都看到假告警。
3. **`ThreadExplosion`/`ThreadLargeExplosion`/`ThreadSmallExplosion` 与 `content/blast/threaded/**` 归属 S3.02/S3.06（任务书裁决）**：
   这 7 个类围绕 1.12 的「每个爆炸一个 `Thread` 子类 + 直接读世界」设计（`ThreadExplosion extends Thread`、`doRun(World, Location)`、
   `Blast blast` 字段、`content.blast.Blast`），与 26.3「快照 + 工作线程 + 主线程预算队列」架构不兼容，且都依赖尚未移植的 `content.blast.Blast`
   （S3.02）。若本步强行移植，只能造出无人调用且仍读写世界的死代码，违反「工作线程绝不改世界」。
   因此账本标记 `MERGED → S3.02 在 LevelSnapshot/BlockEditQueue 上重写（依赖 content.blast.Blast）`（`BlastThreaded` 同）与
   `MERGED → S3.06`（nuclear/thermobaric/antimatter，属于「线程化爆炸与红物质」内容步骤）。`ICBMClassic` 的 P1 TODO 基础库 (9)
   因此写 `（部分：S1.09；…）` 并保持 `[ ]`，与 (7)/(8) 的写法一致。
4. **`BasicResistanceCallBack` 去掉 `blast` 字段**：1.12 持有 `Blast` 只为了传给 `Block#getExplosionResistance(World, BlockPos, Entity, Explosion)`；
   26.3 的 `Block#getExplosionResistance()` 是无参方法（javap 见上），所以字段与构造参数一并删除（保留会引用未移植的 `Blast`）。
   液体判定 `BlockLiquid || IFluidBlock` → `block instanceof LiquidBlock`（26.3 原版类；Fabric 无 `IFluidBlock`，模组流体方块通常继承 `LiquidBlock`，账本已注明）。
5. **`IThreadCallBack` 保留 `Level` 参数**：按任务书「World→Level」照抄 1.12 签名。它本身与「工作线程不得调用以 Level 为参数的方法」冲突，
   故 javadoc 明确「工作线程调用时该参数为 null，实现不得使用」，`BasicResistanceCallBack` 也确实不碰它；这样 1.12 调用点（S3.02 重写时）语义变化可见。
6. **额外挂接 `SERVER_STOPPED → BlockEditQueue.clearAll()`**（任务书只列了 `END_LEVEL_TICK` 与 `UNLOAD` 两处）：与 `RadioRegistry`/`RadarRegistry`
   在本仓库既有的「UNLOAD 清本世界 + SERVER_STOPPED 清全部」模式一致，避免世界卸载事件缺失时残留队列；`clearAll()` 是本步 API 的一部分，否则无调用方。
7. **`LevelSnapshot#getSectionCount()`**：规格外的一个只读访问器（返回已捕获区块段数），让 GameTest 能在「捕获为空」时立即失败并报出可读原因，
   而不是等到超时才报「方块还是石头」。
8. **GameTest 的 `maxTicks = 600`（重要，已在「执行的验证」8 记录）**：Fabric `@GameTest` 默认 `maxTicks = 20`，而 GameTest 服务端的 tick
   远比 20 TPS 快（实测 ≈1.27 ms/tick），20 ticks ≈ 25 ms 墙钟 < 工作线程空闲 `sleep(100)` 轮询间隔，导致测试与 1.12 的 100 ms 轮询赛跑。
   测试改为 600 ticks（≈0.8 s 墙钟上限）后 6/6 稳定通过，且成功路径仍在数个 tick 内结束。**未改动生产代码的 100 ms 轮询**：它对应 1.12 行为，
   实际游戏里约等于最多 2 tick 的启动延迟，属于既有设计。
9. **`WorkerThread.workCount` 由 `int` 改为 `AtomicInteger`**：1.12 的 `int` 由工作线程自减、主线程读取（`addWork` 选负载最低线程）是数据竞争；
   语义不变（仍只计「已入队未启动」的任务），`getWorkCount()` 保留。
10. **`WorkerThreadManager.addWork` 在池已停止时告警并丢弃**：`killThreads()` 之后再有爆炸触发工作时，1.12 会静默入队（永不被执行，爆炸永不完成）；
    现在 `logger().warn` 明确丢弃。加了这层判断所以 `WorkerThread.doRun` 保持 `public volatile`（1.12 原样，未改为私有）。
11. **未加载区块视为空气**：`capture` 对 `getChunkNow == null` 直接跳过（1.12 在未加载位置直接跳过、不复制），`getBlockState` 对未捕获的
    区块段/高度范围外用 `Blocks.AIR.defaultBlockState()` 兜底（规格要求）。
12. **`BlockEditQueue.tick` 从队头按共享预算消费**：每 tick 从一个队列头部连续消费，预算跨 job 共用（一个 job 用不完的预算留给同一 tick 里后面的 job），
    FIFO 保证先提交的爆炸先被处理。`submit` 传入空列表时仍入队，`onComplete` 在随后的 tick（主线程）调用，与 1.12 `EditQueue#doWork` 行为一致。
13. **额外新增 `ConfigThread.BLOCKS_PER_TICK`**：与任务书给的骨架逐字一致（`blocks_per_tick`、`2000`、范围 1..1_000_000）。

## 未覆盖 / 已知限制

- 无图形客户端；本步全为服务端逻辑，无客户端代码。未做长时间（>1 分钟）存活与反复世界卸载的压力测试。
- 未覆盖真实爆炸：`content.blast.Blast` 未移植，`ThreadExplosion` 系列与 threaded 爆炸的重写留给 S3.02/S3.06；
  因此「一套爆炸用快照算出方块并以预算应用」的端到端行为要到 S3.02 才有用例。本步用 gametest 的测试工作
  （只读快照 → 收集位置 → 主线程 action）覆盖同一条管线。
- 工作线程启动延迟：空闲轮询间隔 100 ms（1.12 设计），提交到开始的延迟最坏约 100 ms + 调度；不影响正确性。
- `clear()`/`clearAll()` 丢弃未完成 job 时**不调用** `onComplete`（1.12 `WorldEvent.Unload` 同样直接删队列）；世界卸载时爆炸对象本身也已失效。
- `ThreadWorkBlast` 的 `editPositions` 仍是普通 `ArrayList`（只在工作线程内写、完成后由完成回调读取），未做跨线程同步——与 1.12 一致，
  但 S3.02 在完成回调里若继续在工作线程写该列表需自行注意。
- 未自动化「工作线程里不存在 `level.*` 调用」这一条（按步骤卡用 grep 覆盖，见验证 4）。
